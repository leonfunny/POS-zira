# Android refund coordinator integration review — 2026-09-08

## Result / highest-risk integration fences

Read-only review of the current journal, SQL.js persistence, history importer and login/logout/close-shift paths. No runtime edit in this review. The durable journal is necessary but **not sufficient** to enable refunds safely.

1. **Terminal in memory is not durable terminal.** `confirmAndApply` updates both projection and journal before `flush()`. If that flush fails, the live journal is CONFIRMED while disk may still be UNKNOWN. Likewise a failed REJECTED flush releases the in-memory unresolved index. A coordinator-level storage-failure/recovery latch (or required successful barrier) must block new refunds, close shift, login/logout/tenant clear until flush succeeds or the app restarts and reloads durable evidence. Do not mark confirmed rows UNKNOWN to work around this and do not POST again. Current `clearSalonData` checks only PREPARED/UNKNOWN, so it cannot detect terminal-but-unflushed state.
2. **Close-shift needs a two-sided gate.** Current `real-transport.closeShift` handles missing/closed local shift by immediately issuing best-effort server close; the normal path awaits `syncOrders`, summarizes, marks closed, swallows flush failure and then sends server close. Refund gates must precede even the ghost-shift branch and repeat after the sync await. A shared synchronous operation reservation/mutex must prevent a refund from beginning between the final check and shift closure. Current `orderSyncInFlight` is not a refund mutex. A terminal refund's flush failure also blocks closure even though no unresolved DB row remains.
3. **Cross-shift refund cashflow is not implemented.** `orderRepo.closeShift` selects original orders by `orders.shift_id` and subtracts their cumulative `refund_amount`; it does not use the refund attempt's `shift_id` or refund event time. Refunding an old closed-shift order changes historical figures but is missing from the active shift; imported SERVER orders have NULL shift and are absent altogether. Do not silently assign an imported order to the current shift (that would import its sale too). Either restrict the first enabled refund scope to the original open local shift, or explicitly implement current-shift refund-event accounting before claiming cross-shift/server-order cashflow parity.
4. **Auth recovery versus identity switching.** `loginWithEmail` currently checks only order sync, then cross-salon clear; same-salon user switches bypass the clear guard entirely. Reserve identity changes against an active coordinator operation and recheck after login HTTP but before setting tokens/config. Idle recovery after expiry must allow re-authentication of the same persisted server/salon/user scope; a blanket refusal to log in whenever UNKNOWN exists can make reconciliation impossible. Different user/salon/server must not inherit dispatch authority. `logout` should not mutate identity during a running operation and must not discard unflushed evidence; ordinary logout currently retains the DB.
5. **Backend aliases need recovery lookup as well as locking.** Journal `prepare` locks both local and backend IDs globally, so a second local alias cannot issue another unresolved request. However `findUnresolved(localOrderId)` alone cannot discover the original attempt when UI comes through another alias. Parent should resolve the canonical local order first and/or query unresolved attempts by either local/backend ID, then present the original request ID. Reject scope mismatch rather than constructing a new request. No journal API extension made without parent agreement.
6. **History import is not reconciliation.** Existing `upsertFromServer` protects POS rows by primary/backend IDs, leaves frozen uploads alone, and does not overwrite an existing SERVER row's refund financial fields. That is correct history-cache behavior, but a successful mirror does not resolve an UNKNOWN refund. Use exact authoritative refund validation and journal confirmation. SERVER header/note repair can still run while a refund is awaiting HTTP; freeze expected monetary/identity fields and compare relevant local baseline before applying, or gate imports for that pending order. Do not infer a completed refund from cumulative totals alone.
7. **Projection must be synchronous and cumulative.** Existing `markRefunded` is direct SQL (no nested transaction), but overwrites `refund_lines` and derives timestamp from now. The coordinator callback must use the verified cumulative line audit/amount and must not increment local stock (catalog may already contain backend restock). It must preserve financial/restaurant line identity and execute inside the journal's one transaction. Do not call a method that starts another transaction inside `confirmAndApply`.
8. **The same immutable ID survives every uncertain boundary.** PREPARED flush failure means no POST; retain the frozen row and surface storage error. UNKNOWN must flush before POST. Timeout, transport error, malformed 2xx, context change after dispatch, and post-response validation failure remain UNKNOWN unless authoritative non-execution/rejection is proven. Never release the lock on a generic 4xx/network failure assumption. Confirmation flush failure is handled as point 1. An identical confirmed response must skip projection, but a different JSON response cannot be blindly applied; reconciliation needs deterministic validated response projection or the already-frozen confirmed bytes.

## Minimum coordinator integration points

- `real-transport.refundOrder`: reserve operation before first await; capture identity/config reference/token; resolve original scope and exact local/backend IDs; prepare+flush; UNKNOWN+flush; POST once; validate; confirm+flush; return success only after durable barrier.
- New explicit `reconcileRefund`: reuse only stored original request payload/expected/scope; read/verify authoritative outcome; no new payout, receipt or replacement request. If backend protocol requires replay for idempotency, it is only the same frozen request and must be documented/verified by the parent contract.
- `getRefundDetail`: read-only; expose unresolved request metadata for UI, never POST or auto-reconcile.
- `loginWithEmail`, `logout`, `closeShift`, and cross-tenant `clearSalonData`: reserve/check coordinator busy and storage-failure state. Unresolved per-shift checks include NULL/unknown shift conservatively. Keep same-scope auth recovery possible after operation has stopped.
- `orderRepo.upsertFromServer` / history mirror: no financial refresh as implicit refund confirmation; do not auto-requeue SERVER data.

## Required integration tests

1. Deferred POST + closeShift (including ghost shift) makes zero close HTTP calls and does not mark shift closed; reverse race close-in-progress then refund is refused.
2. Deferred POST + logout/same-salon staff switch/ABA config switch rejects or blocks identity mutation without dropping evidence. Same exact persisted scope can re-login after expiry and see reconciliation.
3. Confirmed/rejected in memory + failed flush blocks close/new request/clear even though the journal has no unresolved row; retry flush does not repeat POST/projection.
4. PREPARED and UNKNOWN barrier failures send zero POST; crash/reload from each durable image keeps the original immutable request ID.
5. Two local aliases for the same backend ID find the original attempt, cannot prepare another ID or refund under another scope.
6. Concurrent history mirror does not overwrite cumulative refund audit; newer authoritative server totals do not count as proof of this request.
7. Old closed-shift and shift-NULL server refund are rejected or covered by explicit event accounting; active cash balance/report includes a supported refund exactly once.
8. Timeout/malformed success/context switch after server effect remains UNKNOWN and reconciliation never shows a fresh payout/print dialog.
