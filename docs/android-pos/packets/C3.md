# C3 — Drain unsynced orders in the background on Android

## Context

On Windows, `src/main/sync/order-sync.ts` runs a periodic drain
(`startPeriodicSync`): a 30-second interval, started after a randomised 0–5s
jitter, with a `stop()` that clears both the jitter `setTimeout` and the
`setInterval`.

Android has **no such timer**. Its only order-sync triggers are:

- `src/renderer/components/pos/PaymentModal.tsx` — one fire-and-forget
  `pos.sync.orders()` right after a payment;
- `src/renderer/components/pos/OrderHistoryModal.tsx` — one call when history opens;
- a manual "sync orders" quick key.

There is also no `online` / `visibilitychange` / app-resume hook.

Consequence, observed on a real device on 2026-08-04: an order whose sync failed
sat unsynced indefinitely — the post-payment shot had already been spent, and
nothing retried it. This compounds with the fact that the tablet reports
`navigator.storage.persisted === false`, so Android is free to evict IndexedDB
and take unsynced sales with it. The app already shows an orange banner warning
about exactly that; nothing was draining the queue behind it.

## Your task

Add a background drain to the Android shell that mirrors the Windows shape.

Requirements:

1. **Interval and jitter**: same as Windows — 30s interval, started after a
   0–5s random jitter. Reuse the constants/shape from `order-sync.ts` so the two
   stay comparable.
2. **Start**: after login completes and the shim transport is live. Do not start
   it in the synthetic/no-transport install.
3. **Stop**: on logout and on session teardown. `src/renderer/android-pos/shim/real-transport.ts`
   already has exactly two such paths, and both run the same trio —
   `billiard.dispose()`, `handoff?.invalidateAuth()`, `entitlements.clear()`:
   one on auth-expiry/session-death, one on explicit logout (which also
   `await agentConnection.disconnect()`). Put the drain stop next to that trio in
   **both** places, so a future teardown path that copies the trio cannot forget
   it.
   `stop()` must clear the pending jitter `setTimeout` as well, so a stop during
   the jitter window cannot leave a timer that arms the interval later. That
   exact bug is guarded against in the Windows implementation — read its `stop()`.
4. **No overlapping runs**: if a drain is still in flight when the next tick
   fires, skip that tick. Do not queue it, do not run two at once.
5. **Do not change** the signature or behaviour of `pos.sync.orders()`, and do
   not remove the existing post-payment or history triggers.
6. Failures inside the drain must be swallowed (logged at debug, like Windows) —
   a background tick must never surface an error dialog to a cashier mid-sale.

Keep it small. This is a timer, not a sync-engine rewrite.

## Tests you must add

New file `tests/android-order-drain.test.ts`, using vitest fake timers:

1. After start + jitter + 30s → the drain ran exactly once.
2. Two ticks → two runs.
3. A drain that has not resolved when the next tick fires → the second tick does
   **not** invoke the drain again; once it resolves, the following tick does.
4. `stop()` → no further runs on subsequent ticks.
5. `stop()` called **during** the jitter window → no interval is ever created
   (advance time well past the jitter and several intervals to prove it).
6. A drain that rejects → the error is swallowed and the timer keeps running.
