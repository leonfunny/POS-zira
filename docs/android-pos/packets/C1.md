# C1 — Restore the billiard stock guards the Android port dropped

## Context

This repo ships one React renderer to two shells: Electron/Windows (`src/main/**`)
and Android/Capacitor (`src/renderer/android-pos/**`). The Android shim was
hand-ported from the Windows main process. Three stock-related guards were
dropped in that port. All three are money-adjacent: they make the tablet's local
inventory drift on every billiard settle.

The rule they encode: **billiard F&B stock is consumed when the item is added to
the table session. Checkout must never deduct it again, and deleting the order
must never give it back.**

## Your task

Fix exactly these three sites. Mirror the Windows reference — do not invent new
semantics, and do not re-implement the shared predicate by hand (hand-copying is
what produced these bugs).

### (a) Checkout must not decrement stock for a billiard order

- Broken: `src/renderer/android-pos/shim/real-transport.ts` — in `createOrder`,
  the local stock-decrement loop (search for `Local stock decrement`). Its
  condition is `if (item.variant_id && item.quantity > 0)`.
- Reference: `src/main/modules/pos.module.ts` — the equivalent loop guards every
  line with `shouldDecrementStockAtCheckout(item, Boolean(billiardRecord))`.
- The shared predicate already exists and is exported from
  `src/shared/pos/order-line-contract.ts`:
  ```ts
  export function shouldDecrementStockAtCheckout(line, isBilliardCheckout): boolean {
    return !isBilliardCheckout && Boolean(line.variant_id) && getLineSaleQuantity(line) > 0;
  }
  ```
  Import and use it. Do not restate the condition inline.
- The billiard flag is available in scope as
  `Boolean(normalizedOrder.billiard_origin_json)`.
- Keep the existing `allowOversell` clamping exactly as it is
  (`MAX(0, ...)` when oversell is off, plain subtraction when on) — that part is
  already a faithful port of `productRepo.decrementStock`.

### (b) Restock must skip lines that were already consumed

- Broken: `src/renderer/android-pos/shim/db/order-repo.ts` — in
  `deleteLocalUnsynced`, the restock loop condition is
  `if (item.variant_id && item.quantity > 0)`.
- Reference: `src/main/database/repos/order-repo.ts`, same function, which adds
  `&& item.inventory_policy !== 'ALREADY_CONSUMED'`.
- Add that term. `inventory_policy` is already persisted on `order_items`.

### (c) A billiard order must not be locally deletable at all

- Broken: same Android `deleteLocalUnsynced` — it has the `backend_id`/`synced`
  guards but no billiard guard.
- Reference: the Windows version refuses first:
  ```ts
  if (order.billiard_origin_json) {
    throw new Error('Billiard POS orders cannot be deleted. Use the owner correction flow.');
  }
  ```
- The Android function returns a result object instead of throwing
  (`{ deleted, restocked, error }`). Follow the Android convention: return
  `{ deleted: false, restocked: 0, error: <the same message> }`. Do not change
  the function's signature or convert it to throwing.

## Tests you must add

New file `tests/android-stock-policy.test.ts`. Follow the harness style of the
existing `tests/android-billiard-handoff.test.ts` (same in-memory database
helper). Cover:

1. Ordinary order, 2 tracked lines → both variants decrement by their quantity.
2. Order carrying `billiard_origin_json` → **no** variant row changes at all.
3. `deleteLocalUnsynced` on an ordinary unsynced order → restocks, returns the
   restocked count, deletes the rows.
4. `deleteLocalUnsynced` where a line has `inventory_policy = 'ALREADY_CONSUMED'`
   → that line is **not** restocked (other lines still are).
5. `deleteLocalUnsynced` on an order with `billiard_origin_json` → refuses,
   `deleted:false`, the order still exists, and no variant row changed.
6. `allowOversell = false` clamps at 0; `allowOversell = true` allows negative.

Each test must assert on the actual `product_variants` rows, not on a return
value alone.
