# C4 — Stop showing a Hold button that can never work

## Context

The retail (grocery) POS toolbar shows **Hold** and **Recall** — park a customer's
basket and bring it back. On Android these are not implemented:
`pos.hold.createCurrent` and `pos.hold.recall` return
`{ success: false, error: 'desktop-only' }` (verified at runtime on a device).

The button in `src/renderer/components/pos/Cart.tsx` is rendered as
`{onHold && (<button ... onClick={onHold}>)}` — it has **no `disabled` prop**, so
it is always live. The failure *is* reported: `handleHoldCart` in
`src/renderer/components/pos/templates/retail/RetailTemplate.tsx` calls
`showToolbarError(result?.error || ...)`. But that error lands in a horizontally
scrollable toolbar strip that is clipped at tablet width and auto-dismisses after
about a second. In a real device run the tester had to read the DOM to discover
the message existed at all.

Net effect for a cashier: a daily till operation looks available, does nothing,
and says nothing.

## Your task

Make the button honest by **not rendering it** where holding is unsupported.

`Cart.tsx` already guards on `{onHold && ...}`, so the cleanest fix is to stop
passing the handler:

1. Expose a capability signal from the shim — e.g. a `supported` boolean on the
   `pos.hold` namespace: `false` in the Android stubs, `true` in the Windows
   preload surface. Keep the shape identical on both platforms; the preload
   parity guard compares method names across the two, so add it to both sides.
2. In `RetailTemplate`, pass `onHold={holdSupported ? handleHoldCart : undefined}`
   and hide the Recall affordance on the same condition.
3. Leave `showToolbarError` and `handleHoldCart` in place. They stay correct for
   Windows, and they remain the right behaviour if a hold ever fails there.

Do **not** implement real Hold/Recall on Android in this packet. Android does
have `src/renderer/android-pos/shim/db/hold-repo.ts`, but it currently serves the
billiard interrupted-cart path; reusing it for user-facing holds is a separate
piece of work.

## Tests you must add / update

1. `tests/android-shell-props-parity.test.tsx` already renders the real
   `AndroidBootApp` and captures the props handed to shared children. Add an
   assertion that the retail surface does **not** receive an `onHold` function on
   Android.
2. Add the mirror assertion for Windows — the desktop shell must still pass
   `onHold` — so this change can never silently remove the feature from the
   counter that actually supports it.
3. `tests/android-preload-surface-parity.test.ts` does not hard-code `pos.hold`;
   it imports the **real** Windows preload (`src/preload/preload.ts`, where the
   `hold:` namespace lives) with an `electron` mock and walks every capability
   path, comparing it against `installShim()`. So adding `supported` to only one
   side will show up there as a parity gap. Add it to both and the test should
   stay green on its own. That registry is **two-way**: a waiver for a gap that
   is now closed also fails the build. Do not add a waiver to get green — if it
   goes red, that is information; report it.
