## Current release verdict

**NO-GO for Android order, payment, shift, print, or fiscal writes.** Read-only catalog discovery with synthetic/non-production credentials may proceed, subject to the tenant-binding decision below. Android remains Staff-JWT-only and CASH-only; it never becomes a print agent.

## Decisions that are already closed for this phase

These are not options to reopen during implementation:

1. **Principal:** Android protected operations use Staff JWT. A device ID is additional context, not a substitute principal.
2. **Payment:** Android order runtime is CASH-only. Electronic tender types may exist only in disabled characterization fixtures.
3. **Print-agent boundary:** Android stores no `pa_` key, sends no `x-print-agent-api-key`, never calls `/print-agent/connect`, never creates/forks a print-agent row, never owns printers, and never opens the agent WebSocket.
4. **Fiscal truth:** Android never reports `PRINTED` from a timeout, local inference, or mere dispatch. Only authoritative terminal status may confirm print.
5. **Retry:** A lost write response reuses the exact persisted key and payload. A retry never generates a new business command merely to escape uncertainty.
6. **Compatibility:** Backend changes are additive or trusted-terminal-scoped. They must not silently break Windows Zira AI 1.0.23 email login, public catalog, current B2B POS routes, or Windows print-agent key routes.

## Required backend acceptance package

Before any Android write flag can become true, the reviewed backend release must include:

- route/controller/service tests for Staff JWT tenant and role enforcement;
- cross-tenant negative tests for staff, shift, order, printer, print job, and fiscal receipt IDs;
- DB-backed idempotency race, payload mismatch, response-loss, and restart tests for order and shift commands;
- Android CASH-only enforcement tests using trusted server-side terminal identity, including spoof attempts;
- bounded refresh, logout, revoke, lost-device, and rotated-token-reuse tests;
- catalog cursor/tombstone tests with failure preserving the last good snapshot;
- stable error-code contract tests;
- server kill-switch tests proving every Android capability defaults false;
- Windows 1.0.23 compatibility tests;
- for fiscal work, real Windows-agent/printer tests in addition to unit tests;
- guarded deployment evidence and verification of the exact built production JavaScript artifact.

No migration/entity change is implied by this document. Device registration, shift idempotency, or provenance may require persistence, but the schema and rollout/rollback plan must be separately reviewed before implementation.
